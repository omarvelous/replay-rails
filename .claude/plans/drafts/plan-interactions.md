# Plan: Interactions (Session-Based Event Tracking for Experiences)

## Problem

The current analytics model is built around ad impressions — a
playlist loops ads, each ad shown is an impression with a duration.
This maps cleanly to passive signage.

Experiences are different. They're interactive, session-based, and
don't have ads. When someone walks up to a kiosk at an open house,
swipes through photos, opens the floor plan, and walks away — none
of that is captured today. The screen show page displays impression
counts that are meaningless when an experience is assigned.

We need an engagement model that captures what actually happens
during an interactive experience session.

## Use Cases

### Agent at an open house

"I had 40 people come through the open house. How many of them
engaged with the screen? Did they look at the floor plan? Did
anyone scan the QR code? How long did people spend on average?"

### Broker evaluating ROI

"We're paying for 3 screens. The window display gets X impressions
per day. The open house kiosk gets Y interactions per event. Which
is driving more leads?"

### Comparing experiences

"The experience for 123 Main St got more engagement than 456 Park
Ave. What was different? More photos? Floor plan attached?"

## Concept: Session-Based Events

An **Interaction** is a discrete event that happens during a kiosk
session. Events are grouped into **sessions** — a session starts
when someone touches the screen (breaking idle mode) and ends when
idle resumes.

### Event types

| Event | Trigger | What it tells you |
|-------|---------|-------------------|
| `session_start` | Touch breaks idle mode | Someone engaged |
| `session_end` | Idle timeout fires | Session duration (end - start) |
| `photo_swipe` | Swipe/tap to next/prev photo | Browsing depth |
| `floor_plan_open` | Tap floor plan button | Interest in layout |
| `floor_plan_close` | Close floor plan overlay | Time spent on floor plan |
| `qr_scan` | Already tracked via QrScan | Handoff to phone |

### What a session looks like

```
Session #1 (duration: 45s)
  09:14:00  session_start
  09:14:03  photo_swipe (photo 2)
  09:14:06  photo_swipe (photo 3)
  09:14:12  floor_plan_open
  09:14:28  floor_plan_close
  09:14:35  photo_swipe (photo 4)
  09:14:45  session_end (idle timeout)

Session #2 (duration: 12s)
  09:22:10  session_start
  09:22:15  photo_swipe (photo 2)
  09:22:22  session_end (idle timeout)
```

### Metrics derived from events

- **Sessions per experience** — foot traffic engagement rate
- **Avg session duration** — how long people spend
- **Photos viewed per session** — browsing depth
- **Floor plan view rate** — % of sessions that opened floor plan
- **QR scan rate** — % of sessions that scanned the QR
- **Bounce rate** — sessions under 5 seconds (walked away)

## Data Model (Draft)

### Interaction

```ruby
class Interaction < ApplicationRecord
  acts_as_tenant :account

  belongs_to :experience
  belongs_to :screen

  validates :event_type, presence: true
  validates :session_id, presence: true
end
```

### Columns

- `account_id` (FK, not null)
- `experience_id` (FK, not null)
- `screen_id` (FK, not null)
- `session_id` (string, not null — UUID generated client-side)
- `event_type` (string, not null)
- `metadata` (jsonb, default: `{}` — event-specific data like
  photo index, duration)
- `created_at` / `updated_at`

### Session grouping

Sessions are not a separate model — they're a `session_id` string
(UUID) generated by the Stimulus controller when idle mode breaks.
All events in that session share the same `session_id`. Aggregation
happens at query time:

```ruby
Interaction.where(experience: exp)
  .group(:session_id)
  .count  # → number of sessions

Interaction.where(experience: exp, event_type: "session_start")
  .count  # → same, more explicit
```

## Client-Side Recording

The `experience_controller.js` already tracks touch events and
idle transitions. It would:

1. Generate a `session_id` (UUID) when idle breaks
2. Fire events via `device-playback` controller to the API
3. Clear `session_id` when idle resumes

### API endpoint

```
POST /api/players/:token/interactions
{
  "experience_id": 123,
  "session_id": "uuid",
  "event_type": "photo_swipe",
  "metadata": { "photo_index": 3 }
}
```

Batched or individual — TBD based on performance. Individual is
simpler and latency doesn't matter for analytics.

## Display

### Experience show page

- Sessions today / this week / this month
- Avg session duration
- Photo views, floor plan opens
- QR scan count (from existing QrScan model)
- Lead count (from existing Lead model)

### Screen show page

- When content is an experience: show interaction metrics instead
  of impression metrics
- When content is a playlist: show impression metrics (unchanged)

### Dashboard

- Interaction metrics alongside impression metrics in the 30-day
  charts (future)

## Open Questions

1. **Rate limiting** — A stuck touch screen could fire hundreds of
   events. Throttle on the client side (max 1 event per type per
   second)? Or server-side dedup?

2. **Privacy** — Should we capture IP address? Useful for unique
   visitor estimation but adds PII considerations.

3. **Retention** — How long to keep raw events? Aggregate into
   daily rollups after 30 days?

4. **Offline** — If the kiosk loses connectivity, queue events
   locally and flush when reconnected? Or accept data loss?

5. **Attribution** — Can we link a session to a lead? If someone
   interacts with the kiosk then scans the QR and submits a lead,
   can we connect the two? Possible via timing correlation or
   a session token in the QR URL.

## Not In Scope

- Real-time dashboard (events displayed as they happen)
- Heatmaps or scroll tracking
- Video/photo analytics (which photos get the most views)
- A/B testing of experience configs
- Interaction-based notifications ("your kiosk got 50 sessions today")
