## The funnel

```
Impressions → Scans → Leads → Contacted
   (saw it)    (scanned QR)  (submitted form)  (agent responded)
```

Each stage has a conversion rate:
- **Impression → Scan** — "How compelling is this ad?"
- **Scan → Lead** — "How effective is the landing page?"
- **Lead → Contact** — "How fast is the agent responding?"

## Impression model

Every time the player advances to a new slide, it fires an impression.
The impression captures a snapshot of every relationship that exists
at that moment — because players move, playlists swap, and positions
change. You can't reconstruct these after the fact.

```ruby
class Impression < ApplicationRecord
  belongs_to :ad
  belongs_to :screen
  belongs_to :player
  belongs_to :site
  belongs_to :playlist, optional: true
  belongs_to :account

  # Denormalized from PlaylistAd at recording time
  # position: where in the playlist this ad appeared (1-based)
  # duration: how long the ad was displayed (seconds)
end
```

### Migration

```ruby
create_table :impressions do |t|
  t.timestamps
  t.references :ad, null: false, foreign_key: true
  t.references :screen, null: false, foreign_key: true
  t.references :player, null: false, foreign_key: true
  t.references :site, null: false, foreign_key: true
  t.references :playlist, foreign_key: true
  t.references :account, null: false, foreign_key: true
  t.integer :position
  t.integer :duration
end
add_index :impressions, [ :account_id, :created_at ]
add_index :impressions, [ :ad_id, :created_at ]
add_index :impressions, [ :screen_id, :created_at ]
add_index :impressions, [ :player_id, :created_at ]
add_index :impressions, [ :site_id, :created_at ]
add_index :impressions, [ :playlist_id, :created_at ]
```

All integers/FKs — still lightweight despite 8 columns. The extra
denormalized fields save expensive joins and impossible
reconstructions later.

### Why capture everything at impression time

Relationships change — if you don't snapshot them, you lose them:

| Field | Why it can't be derived later |
|-------|-------------------------------|
| `player_id` | Players move between screens. "Which device generated these impressions?" is unanswerable after a move. Also needed for device health metrics. |
| `site_id` | Screens could move between sites. Denormalized from `screen.site` for fast site-level aggregation without joins. |
| `playlist_id` | Playlists swap on screens (manual, day-parting). "Which playlist gets more scans?" needs this. |
| `position` | Playlist order changes when reordered. "Do ads in position 1 get more scans than position 5?" is a key optimization question. |
| `duration` | Duration per ad can be changed. Knowing the actual display time at impression time enables "impressions per second of screen time" analysis. |

### What's NOT captured (derivable or irrelevant)

- `listing_id` — too indirect (ad → adable → listing). Query through the ad.
- `agent_id` — even more indirect. Not an impression concern.
- `ad type` — derivable from `ad.adable_type`. Doesn't change.

### How impressions are recorded

The player's slideshow controller fires an event on each slide
transition. The playback controller POSTs to the server.

```javascript
// On slide transition — slideshow controller dispatches event
// with all context needed for the impression
const slide = this.slideTargets[this.currentIndex]
this.element.dispatchEvent(
  new CustomEvent("slideshow:impression", {
    detail: {
      adId: slide.dataset.adId,
      position: slide.dataset.position,
      duration: slide.dataset.duration
    },
    bubbles: true
  })
)
```

The `device_playback_controller.js` already has `recordImpression`
wired up from the API restructure — it listens for
`slideshow:impression` events and POSTs to the API subdomain:

```javascript
// Already in device_playback_controller.js
async recordImpression({ adId, position, duration }) {
  await fetch(`${this.apiHostValue}/players/${this.playerTokenValue}/impressions`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      ad_id: adId,
      playlist_id: this.playlistIdValue,
      position: position,
      duration: duration
    })
  })
}
```

The play view already passes all context as data attributes
(from the API restructure):

### API endpoint

The impression endpoint is `Api::Players::ImpressionsController`
(route already defined in the API restructure, controller to be
created):

```ruby
# POST api.replay.com/players/:token/impressions
# app/controllers/api/players/impressions_controller.rb
module Api
  module Players
    class ImpressionsController < Api::BaseController
      before_action :authenticate_player!

      def create
        screen = @player.screen
        Impression.create!(
          ad_id: params[:ad_id],
          screen: screen,
          player: @player,
          site: screen.site,
          playlist_id: params[:playlist_id],
          account: screen.site.account,
          position: params[:position],
          duration: params[:duration]
        )
        head :created
      end
    end
  end
end
```

The server resolves `player`, `screen`, `site`, and `account` from
the authenticated player (token in URL). The client only sends
`ad_id`, `playlist_id`, `position`, and `duration`.

### Volume considerations

5-ad playlist at 10s/slide = 360 impressions/hour per screen.
3 screens = 15K/day = 450K/month per account. Each row is ~80
bytes (8 integer columns + timestamps) so 450K rows ≈ 36MB/month
per account — manageable.

**v1:** Fire per-slide, async via Solid Queue. Optimize to client-side
batching (accumulate and POST every 30s) if volume is a problem.

## Metric rollups (nightly)

For expensive trend queries, pre-compute nightly via Solid Queue.

### MetricSnapshot model

Uses `starts_at` and `ends_at` datetimes instead of a `period`
string + `period_date` date. The time range is self-describing —
no need to calculate what "daily" means for a given date. The same
schema works for daily, weekly, and monthly rollups without changes.

Metric names are clean — `"impressions"` not `"impressions_daily"`.
The period is encoded in the start/end, not the name.

All snapshots are per-account. Platform-wide metrics are derived
by summing across accounts — no separate platform rows needed.

```ruby
class MetricSnapshot < ApplicationRecord
  belongs_to :account

  validates :metric_name, :value, :starts_at, :ends_at, presence: true
end
```

```ruby
create_table :metric_snapshots do |t|
  t.timestamps
  t.references :account, null: false, foreign_key: true
  t.string   :metric_name, null: false
  t.decimal  :value, null: false
  t.datetime :starts_at, null: false
  t.datetime :ends_at, null: false
end
add_index :metric_snapshots, [ :account_id, :metric_name, :starts_at ]
```

### MetricsRollupJob

3 grouped queries + 3 bulk inserts. No per-account loops.

```ruby
class MetricsRollupJob < ApplicationJob
  def perform(date = Date.yesterday)
    range = date.beginning_of_day..date.end_of_day
    now = Time.current

    bulk_insert("impressions", Impression.where(created_at: range).group(:account_id).count, range, now)
    bulk_insert("scans", QrScan.qualified.where(created_at: range).group(:account_id).count, range, now)
    bulk_insert("leads", Lead.where(created_at: range).group(:account_id).count, range, now)
  end

  private

  def bulk_insert(metric_name, grouped_counts, range, now)
    rows = grouped_counts.map do |account_id, value|
      { account_id: account_id, metric_name: metric_name,
        value: value, starts_at: range.first, ends_at: range.last,
        created_at: now, updated_at: now }
    end
    MetricSnapshot.insert_all(rows) if rows.any?
  end
end
```

**Performance:** 3 `GROUP BY` queries + 3 `INSERT` = 6 queries
total regardless of account count. One insert per metric keeps
each batch focused. Accounts with zero activity on a given day
get no row — absence means zero.

**Platform-wide metrics** are derived from the same data:

```ruby
# Total impressions across all accounts for a date range
MetricSnapshot.where(metric_name: "impressions", starts_at: range.first).sum(:value)

# Or in the admin dashboard
MetricSnapshot.where(metric_name: "impressions", starts_at: 30.days.ago.beginning_of_day..)
              .group(:starts_at).sum(:value)
```

Scheduled nightly via Solid Queue's recurring job configuration.

### When to use live vs rollup

| Data | Source | Why |
|------|--------|-----|
| Screens online | Live query | Real-time status |
| Unread leads | Live query | Real-time count |
| Impressions today | Live query | Includes current day |
| Impressions chart (30d) | Rollups + today live | Fast reads for history |
| Scans chart (30d) | Rollups + today live | Fast reads for history |
| Conversion rates | Rollups | Computed from aggregates |
